Toolbar & status bar — prototype

The prose status line under the toolbar becomes a formatted status bar carrying the connection chip, the bus-health chip, and the same numbers as discrete aligned metrics. The toolbar keeps its buttons; it loses the connection control, which moves into the bar where the connection state already is.

Both themes use the app’s own tokens. Toolbar shape and status-line styling are lifted verbatim from index.css.

While connected: what a live session can report that a file cannot

Frames, elapsed, RAM and cache describe the buffer and are equally true of a loaded file. A few things are knowable only while streaming — but the bar has finite width, so a live-only metric has to be worth more than the standing one it would push out.

Loading a file — two phases, both with a real denominator

Today both phases share one indeterminate sliding chip. Neither needs to be indeterminate:

  • Census — the walk that discovers the frame count. Its total is not known in frames, but the file size is, so it is determinate against bytes read.
  • Import — the pump. scan_blf already returns frame_count, so the denominator is known exactly before a single frame is pumped. This is the tax already paid.
  • Cache rebuild — the series and their sample counts are known, so it is determinate too.

Why bus health is a launcher, not a status chip

It started as a chip reading “Bus health — OK”, and that was wrong three ways. “Health” is a strange word for “this bus is fine”; it overlapped the connection chip, which already says whether traffic is flowing; and with several buses a single summary cannot say which one is off, which is the only thing worth knowing when one is.

So it is a small icon button that opens the panel — the panel is where “which bus” is answered. It stays neutral while every bus is error-active, and tints and grows a count when one is not (), so a bus going off is still noticed without a word for it. The tooltip names the bus.

What the RBS mapping chip reports — and an open question

It is not RBS run status. It is the RBS counterpart of the Signal mapping chip: the notes and warnings across the project’s RBS configurations — a field the resolved DBC does not define, an override naming a signal that no longer exists, a value that will not encode. The badge is that count; no badge means nothing needs attention.

Open: what does clicking it open? It cannot open an individual .cannet_rbs file — a project can have several, and picking one would be the same ambiguity that turned bus health into a launcher. But the RBS signals grid built for task 89 is deliberately scoped to one element, on the grounds that two RBS configs are meant to carry different values and must never be combined.

Proposed resolution: combining is fine for reporting, and forbidden for editing. The chip opens a view that lists every RBS config’s problems together, naming which config each belongs to; acting on one takes you into that config’s own grid, where values are edited one file at a time exactly as today. That keeps the rule task 89 established — the reason configs are not combined is that their values are independent, not that their faults are.

Narrow windows — what drops, and where it goes

The bar is one row and never wraps. A header that grows a second line reflows every panel beneath it, so running out of room is handled by removing things, not by taking more space. Two different things give way, and they give way differently.

Metrics run left to right in priority order — f/s, bus load, frames, elapsed, RAM, cache — and drop from the right. Hovering any metric label shows the full readout, hidden ones included, so a narrow window costs a hover rather than the number. That tooltip also replaces today’s single blob title on the whole status line.

The pinned chips never drop. When the bar runs out of room they collapse into one overflow control carrying the sum of their counts, so something demanding attention can never become invisible — it can only become one click away. It opens as a menu, the same shape the toolbar’s recent-captures dropdown already uses. Click the … below.

Three chips are pinned right, in this order: System messages, Signal mapping, RBS. They are pushed progressively into the menu from the right — RBS first, then Signal mapping, then System messages — so the last one standing is the one that reports faults. The overflow badge sums whatever is inside it, so the tighter bar below reads 3 (RBS mapping alone) and the narrow one reads 9 (2 + 4 + 3).

Settled

  • The connection control moves into the bar. The chip shows the state and pressing it connects or disconnects; the toolbar keeps no Connect button. Nothing reports connection from two places.
  • Notices stay in the bar, with their buttons. Changed-on-disk keeps Reload and Dismiss; the cache rebuild keeps Discard. The bar is a readout that can also carry the response to what it is reporting.
  • Metrics drop right to left, in the priority order above. Hovering any metric label shows the whole readout, hidden values included — and replaces today’s one blob title on the status line.
  • System messages, Signal mapping and RBS are pinned right, in that order, and never drop. When the bar is too narrow they are pushed progressively into an overflow menu from the right — RBS, then Signal mapping, then System messages — badged with the sum of their counts.
