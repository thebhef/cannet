Bus health panel — prototype

The low-level state of a CAN bus is surfaced nowhere today. Most of what this shows already exists and is discarded: InterfaceState — controller state plus the ISO 11898-1 transmit and receive error counters — is defined in cannet.proto, round-trip tested, and forwarded untouched by the server and the proxy, while the client drops it in an ignore arm. The panel is mostly a consumer, not a new model.

Both themes use the app’s own tokens.

The panel

One row per logical bus. Every column is a fact some bus can genuinely supply and some cannot — an in-process virtual bus has no controller and deliberately no configurable bitrate, so it has no counters and no load. Those read —, never a zero and never an estimate.

Bus-off is drawn as 0 % load, not as absent. The controller is off the wire, so zero is the true reading — that distinction matters, because “no traffic” and “we cannot know” are different answers and only one of them is an alarm.

Where the bus-health chip lives

In the status bar directly beneath the toolbar, alongside the connection chip — see plans/prototypes/toolbar-status-bar.html, which is the surface being implemented. There is no window footer. This file covers the panel only.

The chip summarises the worst state across every bus — Bus-off outranks Error-passive outranks OK — so a single bus in trouble is visible without opening anything. Clicking it opens this panel.

Open questions this prototype is meant to settle

  • Adapter column: resolved 2026-08-21 — it shares its format with the project panel. The interface's display_name, then the applied bus configuration rendered by describeAppliedConfig, the same function the project panel already calls to render live: … on a bus row. So 500k · FD data 2M here means exactly what it means there, including driver default (nothing sent).
    Consequence worth knowing: driver and firmware version are not available. The wire's Interface message carries only id, display_name and fd_capable, so anything richer needs new protocol fields — a decision, not an oversight.
  • Does the panel need history? Load over time is a natural plot, and the app already has a plot. Showing a sparkline here may be redundant with plotting bus load as a series.
  • Should a row expand, or is the detail always shown? Chassis is drawn expanded above; the others collapsed.
