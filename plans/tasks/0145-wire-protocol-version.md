# Task 145 — An Explicit Wire Protocol Version

Opened by owner instruction 2026-09-19 from user feedback (ungroomed
item 14). **Executes now, on the current stack.** Grooming in
progress.

## Why

Nothing on the wire says which protocol revision either side speaks.
That was fine while the GUI was the only client and shipped with the
server. It is not fine now that the python client module (task 136)
and its CLI (task 144) exist and third-party clients are the point of
both: a client needs to know which protocol it is speaking and detect
a mismatch instead of guessing, and a third party needs a written
rule for what an upgrade can change so they can migrate. The GUI and
the server keep shipping together; this task is about clarity around
upgrades, not independent development.

## Scope

To groom. Candidate shape:

- a protocol version the server states and every client checks;
- a compatibility rule (what a client does on a mismatch);
- the GUI, the python client, and the CLI all honouring it;
- the rule written down where a third-party client author will find
  it.

## Findings (2026-09-19 survey)

- **Nothing on the wire states a protocol version.** The proto
  package name `cannet.v1` (`crates/cannet-wire/proto/cannet.proto`)
  is baked into gRPC method paths but never read as a version. The
  mDNS TXT `ver=` key carries the *build* string (vergen `git
  describe`), is displayed in the Servers section and the CLI, never
  compared, and is absent for hand-added or `--no-mdns` servers.
  gRPC metadata carries only `authorization`.
- **Mismatch today**: an unknown RPC → `UNIMPLEMENTED`; the GUI's
  `connect_flow.rs` has no arm for it and falls to `Outcome::Retry`,
  so an incompatible server looks like a flapping one and retries
  forever. The python client's `connect.py` raises `Refused(… refused
  the connection: <UNIMPLEMENTED>)`. An unknown `Envelope` variant is
  silently dropped on both sides (no `else` in `session.py`); a
  semantic change to an existing field is undetectable. The clock
  probe's `Unsupported`-by-timeout is the only feature probe.
- **ADR 0051 §6 already commits to the shape**: one monotonic
  version carried by `cannet.proto`, additive changes never bump it,
  breaking ones do, exact match with a clear refusal, no negotiated
  capabilities. It assumes GUI↔server compatibility "already is"
  that predictable — which is false until this task lands. Task 69
  (extensions) plans to consume the same number; this task
  introduces it.
- **Precedent in-repo**: `PROJECT_SCHEMA_VERSION` (ADR 0011) — one
  integer, exact match, reject older and newer with a user-facing
  message.
- **Release trains**: all Rust crates are `0.0.0`, stamped by vergen;
  `release.yml` cuts GUI and server from one tag and the GUI bundle
  contains the server. The three python packages are hand-set
  `0.1.0` and outside the release workflow. The python gencode in
  `libs/cannet-python-wire` is checked in, regenerated by hand, with
  **no CI check** that it matches `cannet.proto`.
- The proto has no `reserved` statements and a hole at `Envelope`
  tag 9.

## Rulings

- **The compatibility rule is the protobuf package-major convention**
  (owner, 2026-09-20). The major lives in the package name
  (`cannet.v1`) and therefore in every gRPC method path. Inside a
  major only additive changes are allowed: new fields, RPCs, oneof
  variants; never renumber, never change a field's type or meaning,
  `reserved` for anything removed. A breaking change is a new
  package (`cannet.v2`) with its own service, served beside v1 for a
  deprecation window so old clients keep working until they migrate.
  Nothing in this task is breaking; every change so far in the
  proto's history was additive, so `cannet.v1` stands. ADR 0051 §6's
  "one monotonic Extension API version" becomes this package major,
  so tasks 145 and 69 share one number. Rejected: a version integer
  with exact match (non-idiomatic; forces every client to upgrade the
  day a breaking change ships) and a min/current range (negotiation
  machinery the package approach makes unnecessary).

Decided by the overseer from the ruling and the codebase, open to
owner reversal:

- **A `ServerInfo` unary RPC in its own stable package** (not in
  `cannet.v1`, so a v2-only server still answers it), unauthenticated
  so a mismatch is reported before a token is asked for. Returns the
  packages served (today `["cannet.v1"]`), the build version, and the
  instance name. Nothing it reveals is new: mDNS already broadcasts
  `ver=` and the name to the LAN.
- **The client states nothing extra.** Its choice of package is in
  every method path it calls; a server answers an unserved package
  with `UNIMPLEMENTED`. Bridges, being clients, need nothing more.
- **A mismatch is terminal.** `connect_flow` gains an outcome that
  does not retry; the Servers section row and the python `Refused`
  message both read "serves cannet.v2; this client speaks cannet.v1".
  An `UNIMPLEMENTED` on any RPC is classified the same way instead of
  falling into `Outcome::Retry`.
- **mDNS gains `proto=`** (comma-separated packages served) so the
  Servers section can grey out an incompatible server before
  connecting; `ver=` stays the build string. Advisory only: absent
  for hand-added and `--no-mdns` servers, so `ServerInfo` is the
  gate.
- **CI enforces the additive rule mechanically**: `buf breaking`
  against the last release tag, plus a check that the checked-in
  python gencode in `libs/cannet-python-wire` matches `cannet.proto`.
- **The rule is written where implementers read**: the header
  comment of `cannet.proto`, and one ADR recording this ruling.
- **The clock probe's timeout idiom stays** as the way to detect an
  additive feature a peer inside the same major may lack.

- **Releases stay lockstep** (owner, 2026-09-20). The point is
  clarity around upgrades for third-party usage and functional
  migration; there is no expectation that the server and the GUI are
  developed independently. `release.yml` is untouched.

- **Small, and placed with the python client** (owner, 2026-09-20):
  this is not a full-day task, and it absorbs into or sits downstack
  of the python client branches (`task136-core-bus`,
  `task136-clock-detect`, `task144-client-cli`). CI does not need
  to run fifty times during development: run the checks once, at
  the tip after the restack, not per intermediate step.
- **The `buf breaking` check and the python gencode drift check stay
  in scope** (owner, 2026-09-20, correcting an overseer cut that had
  moved them to the backlog). The CI ruling above is about cadence,
  not about which checks exist. `buf` is a new CI tool →
  `technology-inventory.md` entry.

## Phases

One phase, one agent, in stack order:

1. **`task145-server-info`**, a new branch inserted directly below
   `task136-core-bus` (above `task141-dbc-search`): the rule in the
   proto header, `reserved 9`, `ServerInfo` in its own stable
   package, the Rust server and the local sidecar answering it, the
   mDNS `proto=` key, the Rust client calling it first with an

   wording and `proto=` grey-out, the ADR, and CI: a `buf breaking`

2. **Amend `task136-core-bus`**: the python client calls `ServerInfo`

   protocol column from `proto=` / `ServerInfo`. Upper stack
   restacked; one tip run of the reached lanes.

## Exit criteria

- `cannet.proto`'s header states the rule: package-major, additive
  only inside a major, what counts as breaking, new package served
  beside the old for a deprecation window. An ADR records it and
  amends ADR 0051 §6 to name the package major as the extension API
  version.
- `ServerInfo` answers on both servers with packages served, build
  version and instance name, without a token; tested on each.
- The Rust client, the GUI, the python client and the CLI each refuse
  a server whose packages exclude theirs with the sentence "serves
  <pkgs>; this client speaks cannet.v1", and the GUI no longer
  retries an `UNIMPLEMENTED`; tested with a fake server that serves
  only `cannet.v2`.
- The Servers section greys out a row whose `proto=` excludes
  `cannet.v1` before any connect; `cannet-client list` shows the
  protocol column.
- CI fails on a non-additive change inside `cannet.v1` (`buf
  breaking` against the last release tag) and on committed python
  gencode that no longer matches `cannet.proto`; both pass at the
  tip. `technology-inventory.md` lists `buf` as adopted.

## Blockers / side effects

- **Inherited, and only fixed further up: 17 source comments under
  `apps/gui/src` name "task 129" at this branch's point in the stack.**
  `CLAUDE.md` § Documentation forbids a source comment citing anything
  under `plans/` or naming a task number. Introduced by `24e76fb6`
  ("Everything the Signal and RBS panels edit is undoable",
  2026-08-30); the `comment-references` grep no longer runs in CI, so
  nothing caught it for three weeks. **`task136-core-bus` already drops
  all 17**, so the grep is clean at the stack tip and nothing is left
  to file — but every branch from `feedback-capture` to
  `task141-dbc-search` carries them, which is what a reviewer walking
  the stack will see.

- **Inherited: `apps/gui/src-tauri/src/interfaces.rs` was not
  rustfmt-clean.** Three hunks, from `7d18a421` ("A stored trust answer
  is dialled at once, and retries stop repeating themselves"). CI runs
  no `cargo fmt --check` — only the pre-commit hook formats, and
  `--no-verify` skips it — so an unformatted file can ride in. Fixed on
  this branch rather than reported and left: it is a mechanical
  rustfmt run, and leaving it would make this phase's own
  `cargo fmt --all -- --check` red.

- **The token gate is per service, not server-wide.** See the phase-1
  status-log entry: `ServerInfo` has to answer without a credential and
  a tonic interceptor cannot see which service a call is for, so the
  exemption could not live in the layer. Nothing is ungated today, and
  `crates/cannet-server/tests/auth.rs` is the guard, but "adding a
  service cannot accidentally add an ungated one" is no longer true by
  construction.
