# Task 87 — BLF Writer Timestamp Fidelity

Opened by owner ruling 2026-08-19, from a side finding of task 86
phase 1. `BlfCaptureWriter` **silently clamps a frame that precedes the
first frame appended**, so a saved BLF can differ from the capture it
was written from — with nothing said.

## The defect, as measured

Task 86 phase 1's experiment: writing `[+1000 ms, +500 ms, +1100 ms]`
reads back `[+1000 ms, +1000 ms, +1100 ms]`. The out-of-order frame
gains 500 ms it never had.

> **Corrected by phase 1.** This task was opened describing the clamp
> as firing on "a frame whose timestamp is earlier than the one before
> it". It does not. The writer anchors `measurement_start_time` on the
> **first** frame appended and compares every later frame against that
> anchor, so a descent that stays above the anchor is written and read
> back exactly — `[+0, +1000, +500, +1100]` ms round-trips unchanged.
> This is an *anchor* bug, not an *ordering* bug, and the distinction
> decides the mechanism: fidelity needs no reordering, only an anchor
> at or below the capture's minimum. See the phase-1 status log.

This is not a synthetic edge case:

- ADR 0024 already records real multi-bus captures dipping **~1.1 s
  below their own running maximum, several times a minute** — device
  clocks on separate interfaces do not agree, and arrival order is not
  timestamp order.
- Save Capture writes the store in **arrival** order, so a capture
  whose earliest frame is not its first-arriving one is clamped.
- The corruption lands in a file that leaves the tool. Of everything
  the 81 / 86 / 27 cycle surfaced, this is the only item that damages
  data handed to someone else.

## Research first — the mechanism follows from the answer

The fix is not obvious until the format question is settled, and
choosing a mechanism without it risks writing files other tools read
differently:

1. Does the BLF container format **permit** non-monotonic
   `object_timestamp` values? Vector's own writers, and what their
   readers do with a decreasing stamp, are the evidence — not our
   reader alone.
2. What does *our* reader do today? `crates/cannet-blf` reads objects
   in file order and adds `measurement_start_time`; nothing in the read
   path appears to require monotonicity, but that must be confirmed
   rather than assumed.
3. Does anything else depend on the ordering the clamp currently
   guarantees — the log-container index, the scan's first/last
   (now min/max, task 86 phase 1), seek behaviour?

Only then choose between:

- a **bounded reorder window** (buffer N frames or T milliseconds and
  emit in timestamp order — cheap, bounded memory, still clamps a dip
  deeper than the window);
- a **two-pass write** (exact, costs a second pass over the capture);
- a **seek-back** correction (exact for the container, awkward against
  a streaming writer that renames `.part` into place).

## Scope

- The format verdict, written down where the next reader will find it
  (`docs/blf-feature-support.md` is the existing home for what our BLF
  support does and does not cover).
- The writer change, whichever mechanism the verdict admits.
- If any clamp survives by design (a dip deeper than a bounded
  window), it is **reported, not silent** — a system-log warning naming
  the frame and the error.

- The format question is answered with evidence and recorded.
- A capture containing out-of-order timestamps round-trips through

  the existing fixture.
- Any surviving clamp is logged, never silent; tested.
- `docs/blf-feature-support.md` states the writer's ordering guarantee.

## Blockers / side effects

- **`WindowedSource` truncates an out-of-order import** (pre-existing,
  not caused by the writer). `cannet_core::WindowedSource` stops the
  walk at the *first* frame past `end_ns` and never calls the inner
  source again, documented as "matching a file's arrival-ordered
  timestamps". Measured on `examples/time-origins/wall-clock-out-of-order.blf`
  (experiment 8 below): importing with `end_ns = start + 1000 ms` keeps
  31 of 121 frames and silently drops the file's two *earliest* frames
  (+120 ms, +300 ms) even though both are inside the requested window.
  The clamp this task removes never protected this — a dip that stays
  above the writer's anchor already survives into our own files today
  (experiment 2). Not in this task's scope; needs its own decision
  (walk to EOF and filter, or state the truncation in the dialog).

- **`FileStatistics.last_object_time` is the last object appended, not
  the latest** (experiment 3). It is stamped from
  `BlfFileWriter::last_unix_nanos`, which each `append_object`
  overwrites unconditionally. With a dip as the final frame the header
  understates the capture's end, and with input `[+1000 ms, +500 ms]`
  the header's own span inverts — `measurement_start_time` (+1000 ms)
  is *later* than `last_object_time` (+500 ms) (experiment 6). A
  third-party tool that sizes its timeline from the header alone gets
  a negative duration. Small enough to fold into phase 2 (make it a
  running max) rather than raise as separate work.

## Status log

### 2026-08-19 — Phase 1 (research: does BLF permit non-monotonic object timestamps?)

Branch `task-87-phase-1-blf-ordering-research`, off
`task-27-phase-3-rbs-watch`. No runtime code changed.

#### Investigation

**Observation 1.** `frame_to_object_bytes` (`crates/cannet-blf/src/lib.rs`)
encodes `rel_ns = frame.timestamp_ns.saturating_sub(start)`, where
`start` comes from `BlfFileWriter::set_start_if_unset` — a
`get_or_insert` that latches on the **first** call and never changes
again. `append_marker` does the same. The `saturating_sub` therefore
compares each event against the *anchor*, not against its predecessor.

**Hypothesis 1.** The clamp is not triggered by non-monotonicity at
all. It fires only when an event is earlier than the **first event
appended**; a dip that stays above that anchor is written faithfully,
out of order, and read back out of order.

**Experiment 1.** Round-tripped two frame sequences through
`BlfCaptureWriter` → `BlfCanFrameSource` → `scan_blf`: the task's own
`[+1000 ms, +500 ms, +1100 ms]`, and `[+0, +1000 ms, +500 ms, +1100 ms]`
— the same descent with an earlier frame in front of it. If hypothesis
1 is wrong, both lose the dip.

**Data 1.**

| appended | read back |
| --- | --- |
| `[+1000, +500, +1100]` ms | `[+1000, +1000, +1100]` ms |
| `[+0, +1000, +500, +1100]` ms | `[+0, +1000, +500, +1100]` ms |

**Conclusion 1.** Hypothesis 1 confirmed, and it **refutes the framing
this task was opened with**. "A frame stamped earlier than its
predecessor is written at the anchor" is not what happens: a frame
earlier than the *anchor* is. The bug is an anchor bug, not an ordering
bug — which means **fidelity does not require reordering anything**. It
requires only that `measurement_start_time` be at or below the
capture's minimum.

**Experiment 2 (how far the anchor problem reaches).** Appended 40 000
frames from `+5000 ms` — enough that several `LOG_CONTAINER`s are
deflated and on disk — then one frame at `+1000 ms`.

**Data 2.** The final frame read back at `+5000 ms`: 4 s lost, with the
containers that would have to change already compressed on disk. A dip
can arrive arbitrarily far into the capture.

**Experiment 3 (the header's own span).** Same round trip, reading
`FileStatistics` rather than the objects.

**Data 3.** `[+0, +1100, +500]` ms → header `last_object_time = +500 ms`
while the file's newest event is at `+1100 ms`. `[+1000, +500]` ms →
`measurement_start_time = +1000 ms`, `last_object_time = +500 ms`: the
header's stated span is inverted. Recorded under *Blockers / side
effects*.

**Experiment 4 (markers).** Appended a frame at `+1000 ms`, then a
marker at `+200 ms`.

**Data 4.** The marker reads back at `+1000 ms`. Notes clamp exactly as
frames do.

##### Question 2 — what does our reader do today?

**Experiment 5.** Walked `examples/time-origins/wall-clock-out-of-order.blf`
(121 objects, the earliest three at the *end* of the file) through the
full decoding `BlfCanFrameSource`, and separately through `scan_blf`.

**Data 5.** All 121 objects decode; exactly one descent
(`+2460 ms → +120 ms`) is delivered as-is; no error, no warning, no
reordering. `scan_blf` reports min `+120 ms` / max `+2460 ms`.

**Conclusion 2.** Confirmed by measurement rather than assumed: the
read path has no monotonicity dependency anywhere. `BlfReader` is
strictly sequential — it never seeks, builds no index, and reads no
restore points (cannet writes `restore_points_offset = 0`).
`scan_blf`'s span is already a min/max over the walk. Kept as
`crates/cannet-blf/tests/ordering.rs`.

##### Question 1 — does the format permit it?

**Answer: permitted by silence, and demonstrably produced and consumed
in practice.** The evidence is in `docs/blf-feature-support.md`
§ "Object timestamps and ordering". In short:

- There is **no published BLF specification**; every open
  implementation is reverse-engineered from Tobias Lorenz's C++
  library. Vector's one public API document, the *BINLOG DLL Manual*
  v1.5, states no ordering requirement and does not even document the
  `mObjectTimeStamp` field.
- **Technica's `vector_blf`** (this repo's own oracle, source read at
  the pinned upstream): `File.cpp` never reads `objectTimeStamp`; the
  library has no sort and no ordering check.
- **Wireshark** (`wiretap/blf.c`): no ordering check, and its
  log-container index is keyed on **file position**, not time.
- **`python-can` 4.6.1** — measured, not just read. Its `BLFReader`
  reads our out-of-order fixture completely and silently (121 objects,
  the descent intact). Its `BLFWriter` given `[+0, +1000, +500,
  +1100]` ms writes and reads back exactly that — an independent
  writer *emitting* a decreasing `objectTimeStamp`. Given
  `[+1000, +500, +1100]` ms it produces `[0, 0, +100]` ms: python-can
  has the **identical anchor bug**, `max(timestamp, 0)` against an
  anchor latched from its first object.
- The format anticipates mixed provenance: header version 2's
  `timeStampStatus` carries a per-object `SwHw` bit and an
  `originalTimeStamp` field.

**Not established, stated plainly.** Whether Vector's own CANoe /
CANalyzer sort, warn, or misbehave on a descent — those tools are not
available here, and Vector's KB renders article bodies through
JavaScript. The `vector-blf-oracle` feature would give a third-party
C++ reader's verdict directly, but its build script produces a
`.so`/`.dylib` and needs cmake plus a C++ toolchain; neither is present
on this Windows host, so it must run on Linux CI. The one
ordering-adjacent Vector API is `BLSeekTime` ("seek forward … to the
first object with a certain time stamp"), whose usefulness implicitly
assumes ascent — so the residual risk is a *time-seeking Vector
consumer landing somewhere surprising*, not unreadability. Nothing in
the container framing, object framing, or any index depends on order.

##### Question 3 — what depends on the ordering the clamp guarantees?

Nothing that the clamp actually protects.

- **Log-container index** — there is none. Containers are read strictly
  in file order, and `restore_points_offset` is written as 0 and never
  read. Wireshark's index, the one real-world example, sorts on file
  position.
- **`scan_blf`'s span** — already min/max, not first/last.
- **`TraceStore::frame_index_at_ns`** binary-searches the store and its
  doc comment claims "frames are appended in arrival order with
  monotonic timestamps" — which the store's own test
  `live_edge_is_the_newest_frame_not_the_last_appended_one` contradicts
  in the same file. That is a live-capture condition already, not one
  the BLF clamp creates; noted under *Blockers / side effects*.
- **`cannet_core::WindowedSource`** is the one genuine ordering
  dependency, and the clamp does not protect it — data 1 shows a dip
  above the anchor already reaches our own files. Measured separately;
  recorded under *Blockers / side effects*.

#### Mechanism recommendation — two-pass write, in its "declare the anchor" form

Fidelity needs one thing: `measurement_start_time` at or below every
event. Not sorting. The recommendation is therefore a two-pass write in
which pass one computes only that minimum and hands it to the writer
before the first append — the writer stays streaming and stays `.part`.

**Why it costs almost nothing here.** `save_capture` already
materialises the whole frame set (`trace_store.slice(0, len)`) before
calling `write_blf_capture`, so the min is an `O(n)` scan over memory
that is already resident. More to the point, `write_mdf_capture` in the
same file **already runs exactly this pass** — MDF's `hd_start_time_ns`
has the identical non-negative-offset constraint, and its pass one
takes the min over frames, notes, and signal samples before opening the
writer. BLF is the odd one out. The change is a way to declare the
start on `BlfCaptureWriter` (rather than latching it from the first
append), one caller update, and `last_object_time` becoming a running
max.

**Why not a bounded reorder window.** It solves a problem the format
does not pose. Reordering buys no fidelity (data 1), the anchor would
still be whatever the window's minimum happened to be, and data 2 shows
a dip arriving 40 000 frames in — past any bounded window. It also adds
a reorder buffer to a writer that has neither, and disturbs
`write_blf_capture`'s frames-vs-notes merge, which presumes sorted
frames. Strictly more cost, strictly less fidelity.

**Why not seek-back.** It cannot do the job. The header *is* already
rewritten at `finish` — `BlfFileWriter::finish` seeks to 0 and
overwrites `FileStatistics` — so lowering `measurement_start_time` is
free. But every already-written object's `objectTimeStamp` is a
relative offset that would have to gain the same delta, and those
objects are zlib-deflated inside `LOG_CONTAINER`s already on disk
(data 2). Correcting them means inflating, rewriting and re-deflating
every container: a full rewrite, not a seek-back, and it fights the
streaming shape exactly as the task suspected.

**Considered and not recommended: anchor headroom.** Anchor at
`first − H`, so dips up to `H` are representable with no second pass
and no buffering. Cheap and streaming-friendly, but it stamps a
`measurement_start_time` no event corresponds to, and still clamps
beyond `H`. Worth reaching for only if a future caller genuinely cannot
know its minimum.

**The surviving clamp.** Under this recommendation the GUI's save path
can no longer clamp, because it declares the true minimum. What remains
is the fallback for a caller that appends without declaring one. Phase
2 should keep that fallback and make it loud: the writer records the
clamp, and the caller emits a `capture`-tagged `sys_warn!` naming the
frame (channel, id, timestamp) and the error in ms. In the GUI it
should never fire — that is the point; it guards a future caller, not
today's.
